# 레거시 그룹웨어 전자결재 DX — 신청서 구조화와 근태 자동 판정 연동

> 15년 된 JSP 그룹웨어의 전자결재 양식 하나를 "에디터 안의 HTML 표"에서 "구조화 데이터"로 바꾸고,
> 그 데이터를 ERP 일 근태 배치에 연결해 그동안 존재하지 않던 지각 자동 판정을 신설했습니다.
> 화면·SQL 매퍼·스토어드 프로시저·배치 잡·데이터 이관까지 혼자 설계하고 반영했습니다.

## 1. 배경 — 데이터가 "그림"으로만 있었다

유연근무제 신청서는 전자결재 양식 중 하나로, 직원이 출퇴근 유형과 적용 기간을 골라 상신합니다.
그런데 이 양식은 **에디터 안에 HTML 표를 문자열로 만들어 넣고, 사용자가 표 안의 라디오를 눌러 저장하는** 구조였습니다.
저장되는 건 HTML 덩어리 하나뿐이었습니다.

그 결과:

- **누가 어느 유형으로 언제부터 언제까지 신청했는지 쿼리로 알 수 없었습니다.** 현업 담당자가 문서를 하나씩 열어 눈으로 확인해야 했습니다
- 목록에는 제목과 결재 상태만 나왔고, 같은 기간 중복 신청을 막을 근거가 없었습니다
- 저장·삭제 로직에 이 양식의 분기가 아예 없어 결재 마스터만 남고 있었습니다
- ERP 일 근태에는 **지각 계산 자체가 없었습니다.** 4개월치 2만여 행을 실측했더니 지각 시간이 채워진 행이 0건 — 컬럼은 있지만 채우는 로직이 처음부터 없었습니다

현업 요구는 "유연근무 신청자는 본인 유형 기준으로, 나머지는 표준 출근시각 기준으로 지각을 자동 판정해 달라"였습니다.
그러려면 먼저 신청 데이터가 구조화되어야 했습니다.

## 2. 설계 원칙

**하위호환을 깨지 않는다.** 전환 이전에 상신·완결된 570건은 화면·인쇄가 전과 동일해야 하고, 결재 진행 중인 문서가 오류 나면 안 됩니다.

**기존 결재 인터페이스를 건드리지 않는다.** 다른 근태 양식들은 최종결재 시 근태 이벤트 테이블에 행을 쓰는 공통 경로를 탑니다.
유연근무는 "그 날의 이벤트"가 아니라 "기간의 기준값"이라 성격이 다르고, 그 테이블에 넣으면 다른 처리 로직과 경합해 실제 근태를 가립니다.
대신 결재 마스터의 승인 상태를 읽도록 해서 **반려·삭제·상신취소 시 원복이 자동으로 따라오게** 했습니다.

**정책 값은 DB에 남긴다.** 유형별 시각 정의는 한 곳에만 두되, 저장 시 선택된 시각을 그대로 DB에 기록해 나중에 유형표가 바뀌어도 과거 문서 표시와 지각 판정이 변하지 않게 했습니다.

## 3. 구현

### 3-1. 양식 구조화 (DX 전환)

```
전환 전   에디터 HTML 표  ──▶  결재 본문 (문자열)

전환 후   폼 컨트롤(라디오·datepicker·textarea)
            ├─▶ 전용 상세 테이블 (유형·출퇴근시각·적용기간·사유)
            └─▶ 결재 본문 스냅샷 (인쇄·열람용)
```

- 신규작성·상세·상신수정·복사를 한 JSP가 겸하는 구조에서 문서번호 유무 + 상세 행 유무로 **구조화 폼 / 레거시 렌더** 를 분기. 상세 테이블이 없거나 조회가 실패해도 레거시 경로로 떨어져 기존 문서는 항상 열립니다
- 저장 분기는 구조화 필드가 비어 있으면 상세 INSERT를 건너뛰어, 이전 문서를 상신수정해도 빈 행이 생기지 않게 방어
- 목록에 신청유형·적용기간 컬럼 추가, 결재완료 문서와의 기간 겹침 확인 AJAX 신설
- 인증 체크가 빠져 있던 화면에 정상 인증 체크 추가
- 신규 쿼리는 전부 파라미터 바인딩 — 레거시에 남아 있는 문자열 치환 패턴을 신규 코드에는 쓰지 않는 규칙을 문서화

### 3-2. 레거시 문서 570건 이관

본문 HTML 표를 파싱해 구조화 테이블로 옮기는 Python 스크립트를 작성했습니다.

| 구분 | 건수 |
|---|---|
| 자동 파싱 | 534 |
| 수기 보정 (현업이 엑셀로 채운 값을 파서가 병합) | 33 |
| 제외 확정 (테스트·미상신·유형 미선택) | 3 |
| **이관 완료** | **567 / 570 (99.5%)** |

- **유형은 문자가 아니라 시각으로 매핑.** 구형 문서는 유형이 3종, 현행은 5종이라 같은 이름의 유형이 다른 시각을 가리킵니다. 문자를 그대로 옮기면 틀리므로 시각 기준으로 재매핑
- 트랜잭션 + 존재 확인 가드로 재실행 안전, 이관 ID로 일괄 원복 가능
- 이관 후 검증: 시각·날짜 형식 오류 0건, 사번 누락 0건, 유형↔시각 정합 100%

### 3-3. 일 근태 지각 계산 신설 (T-SQL)

```
[현행]  카드리더 + 외부 원시근태(링크서버) + 근태신청 + 출장(링크서버)
          → 일근태 생성 SP → 일 근태 테이블           ※ 지각 미설정

[신설]  일 근태 + 유연근무 상세(승인분) + 근무시간 기준
          → 지각 계산 SP → 일 근태.지각시간 + 근태코드

[배치]  사업장 루프 래퍼 SP → SQL Agent Job 매일 새벽
```

기준 출근시각 우선순위:
1. 유연근무 신청 (개인·기간별, 결재완료분만). 같은 기간에 여러 문서가 있으면 **시작일이 늦은 문서 우선** — 기간 중간 변경을 재신청으로 처리하는 근거
2. 사업장별 근무시간 기준 테이블
3. 둘 다 없으면 표준 출근시각 — 실측 결과 대부분의 사업장이 기준 미등록이라 이 경로가 실제 주경로

설계 중 확인한 함정과 대응:
- **ERP의 "일근태 생성" 버튼이 지각을 지운다.** 기존 SP가 해당 기간 행을 삭제 후 재생성하기 때문. 기존 SP 맨 끝에서 신규 SP를 호출하도록 패치해 버튼을 눌러도 지각이 유지되게 함
- **링크서버 장애 시 배치 전체가 죽는다.** 링크서버 조회 두 곳을 TRY/CATCH로 감싸 장애 시 해당 소스만 빠지고 나머지는 진행
- 근태코드가 있는 날은 판정 제외, 야간조 제외, 개인 예외자 테이블로 관리, 시운전 모드로 UPDATE 없이 대상만 조회
- **급여 무영향 검증**: 지각 코드가 급여 계산에 매핑되지 않음을 확인한 뒤에 코드 세팅을 결정

### 3-4. 신청 정책 개정 3회

현업과 협의하며 규칙이 세 번 바뀌었습니다. 처음엔 화면·매퍼·DB CHECK 제약 3층으로 신청 기간 차단을 걸었다가,
운영 요구에 따라 "저장은 항상 허용, 상신 시에만 조건부 검증"으로 완화했습니다.

- 검증 위치를 저장(입력 완결성)과 상신(정책)으로 분리
- 3층 차단을 전부 제거하고 정책을 화면 한 곳으로 모아 다음 변경 비용을 낮춤
- 시스템 전환 유예를 위한 한시 해제(기한 도래 시 자동 원복) 옵션 제공

## 4. 운영 반영

- **개발 VM → 운영 이관 절차서** 작성: 객체 6개 + 잡 1개의 의존 순서, DB명 치환 위치, 기존 SP 덮어쓰기 전 diff 필수 등 함정 4개 명시
- 사전조건 쿼리(급여 매핑 확인 등) 중 하나라도 어긋나면 중단하는 게이트
- 이관 후 검증 쿼리 세트: 객체 존재 → 패치 삽입 여부 → 시운전 → 정합성(지각시간과 근태코드 불일치 0건)
- 배치 실행 로그 테이블로 일별 실행 추적, 휴가 반영 점검 스크립트 추가

## 5. 함께 정리한 것

이 작업을 하면서 그룹웨어 전체의 운영 기반도 같이 세웠습니다.

- 소스 관리 체계 정비 — 날짜 접미사 백업본 정리, 웹루트에 남아 URL로 실행되던 백업 파일 목록화
- 전자결재 화면별 카탈로그(양식 코드·상태 코드·테이블·SP 사전)와 화면별 SQL 사본 규약 신설 — 쿼리가 SP에 숨어 있어 찾지 못하던 문제 해소
- 설정·매퍼 경로 불일치로 발생하던 전 페이지 장애 패턴 문서화
- Claude Code 에이전트·훅 구성으로 AI 보조 개발 — 설정 파일 열람 차단, 위험 셸 명령 가드, DB 조회 보고 시 실행 SQL 동반 규약

## 6. 회고

- **잘한 것**: 코드를 짜기 전에 실측부터 했다. "지각 계산이 안 된다"는 요구를 "원래 없었다"로 바로잡았고, 기준 테이블이 대부분 사업장에 없다는 것을 알았기에 기본값 경로를 주경로로 설계할 수 있었다
- **잘한 것**: 기존 인터페이스를 우회하지 않고 이유를 문서에 남겼다. 다음 사람이 "왜 공통 경로를 안 탔지?" 하고 되돌리지 않도록
- **아쉬운 것**: 적용기간 규칙이 화면 JS에만 있다. 직접 POST하면 규칙 밖 값이 저장된다 — 서버 검증을 추가해야 한다
- **아쉬운 것**: 목록이 행마다 상세를 조회한다(N+1). 공통 목록 쿼리를 건드리지 않으려 택한 타협이라 전용 목록 쿼리로 바꿔야 한다
